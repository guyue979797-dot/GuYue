# InfoLens 前端开发原则

> 文档版本：1.0\
> 生效日期：2026-08-02\
> 适用对象：产品、前端开发、代码评审、测试及参与前端修改的 AI 工具\
> 强制级别：前端功能开发、缺陷修复和重构开始前必须阅读并完成检查

## 1. 原则的使用方式

任何前端任务必须按以下顺序执行：

1. 阅读本文。
2. 阅读《鑫向晨 CRM 设计规范》最新版本。
3. 涉及结构调整时阅读《前端代码重构要求》最新版本。
4. 确认业务行为、视觉标准、复用组件和验收用例。
5. 完成“开发前置检查”后才能编码。

禁止先写代码、出现问题后再用 CSS 补丁修正。

## 2. 原则优先级

发生冲突时按以下优先级判断：

1. 已书面确认的最新业务需求和数据口径。
2. 用户现有关键业务流程、权限和可交互能力不得丢失。
3. 本文的工程与交互原则。
4. 《鑫向晨 CRM 设计规范》。
5. 页面局部历史实现。

如果最新业务要求偏离设计规范或本文，必须登记例外，禁止开发人员自行猜测。

## 3. 十二条强制开发原则

### 原则一：先确认行为，再调整视觉

- 重构或视觉优化不得删除原有点击、钻取、导出、筛选、权限和键盘能力。
- 修改前列出“必须保留的业务行为”。
- 不清楚的数据口径和交互必须先确认，不能用视觉推断业务。

### 原则二：Arco 原生能力优先

- Table、Modal、Select、Input、Pagination、Typography、Dropdown、Tag、Empty、Spin 优先使用 Arco。
- 禁止在 Arco 已提供稳定能力时再手写第二套组件。
- 对 Arco 进行 CSS 覆盖前，必须先检查真实 DOM 和官方组件能力。
- 不依赖 Arco 偶然生成的深层 DOM 顺序完成业务样式。

### 原则三：同一功能只有一个实现

- 禁止复制 DOM 实现冻结列、固定操作区或视觉遮罩。
- 禁止一张表同时存在原始表格和覆盖表格。
- 禁止同类截断、分页、弹窗滚动、行操作各页面单独实现。
- 新实现上线前必须删除被替代的旧逻辑和旧样式。

### 原则四：先复用，再新增

开发新组件前必须搜索：

```bash
rg "组件名|相似功能|className" frontend/src
```

- 能通过 props 扩展现有组件时，不创建重复组件。
- 只有一个页面使用、且没有稳定通用职责的内容保留在 feature 内。
- 通用组件不得包含客户、政策、产品等具体业务字段。

### 原则五：按业务域隔离代码

- 新功能进入 `features/<业务域>/`，不得继续堆入 `App.jsx`。
- 页面、Filters、Table、Modal、hook 和 API 按职责拆分。
- Feature 不直接修改其他 feature 的内部状态和样式。
- `App.jsx` 只承担应用壳、会话、权限入口和页面组合。

### 原则六：设计系统是唯一视觉来源

- 颜色、字号、间距、圆角和阴影必须来自 `tokens.css`。
- 先查设计规范和 Token，再写 CSS。
- 禁止为了匹配单张截图大量硬编码像素和颜色。
- 颜色只表达状态语义；名称、人员、地址等普通信息使用中性色。
- 所有 margin、padding 原则上使用 4px 网格。

### 原则七：CSS 必须精准、可删除

- Feature 样式以页面根类开头。
- 禁止裸写 `table`、`td`、`th`、`button`、`input` 等全局选择器。
- 禁止使用 `nth-child()` 表达字段语义。
- 禁止用 `last-child` 推断操作列。
- 禁止无说明使用 `!important`。
- 禁止新增 `legacy.css` 规则。
- 每条规则必须能够定位到明确组件，并可随组件删除。

### 原则八：表格只有一个布局和滚动模型

- 业务数据表统一使用 Arco Table 和统一 DataTable 容器。
- 列宽必须遵循[表格设计规范](./表格设计规范.md)：按可见内容计算、限制自动最大宽度、支持拖动与恢复；不再由业务页面手写普通固定列宽。
- 固定列由 Arco `fixed` 实现；非必要不冻结。
- 一张表只能有一个纵向滚动容器。
- 禁止“虚拟滚动 + 左右双 fixed”。
- 必须验证 Mac 触控板触顶、触底和横向边界。
- 常规单元格必须限制溢出，操作列例外必须显式声明。

### 原则九：截断和弹层使用稳定方案

- 表格截断统一使用 `Typography.Text ellipsis`。
- 禁止在 td 中用独立 Tooltip 包裹截断文本。
- Tooltip、Dropdown、Popover 统一挂载到 `document.body`。
- Modal 只允许内容区滚动，Header/Footer 固定。
- 弹层打开后必须验证页面滚动、表格滚动和窗口缩放。

### 原则十：交互必须可发现、可访问

- 可点击数字、标签和状态使用 `<button type="button">`。
- 图标按钮必须有 `aria-label`。
- 不以颜色作为唯一状态信息。
- 行操作固定为一个主操作加“更多”菜单。
- 键盘必须能够访问筛选、详情、菜单、分页和弹窗按钮。

### 原则十一：状态和请求必须可预测

- 区分编辑中的筛选条件与已经应用的筛选条件。
- 查询、重置和 pageSize 变化回到第一页。
- 防止旧请求覆盖新请求。
- loading、empty、error、success 状态必须完整。
- API 错误必须向用户展示，不能只输出控制台。
- 不在 render 中发送请求或修改状态。

### 原则十二：每次修改都必须闭环

- 实现功能。
- 删除旧实现和无引用代码。
- 构建检查。
- 关键交互回归。
- 记录例外和风险。
- 提交内容保持单一目的并可回滚。

只新增代码、不清理旧实现，视为任务未完成。

## 4. 开发前置检查（Definition of Ready）

以下项目未全部确认，不得开始编码：

- [ ] 已阅读本文和最新设计规范。
- [ ] 已明确任务涉及的页面、角色、接口和数据字段。
- [ ] 已列出必须保留的原有业务行为。
- [ ] 已定义正常、空数据、加载、错误和禁用状态。
- [ ] 已搜索现有组件，确认复用或新增方案。
- [ ] 已确定使用哪些 Arco 原生组件。
- [ ] 已确认表格列宽、是否滚动、是否固定列和分页方式。
- [ ] 已确认弹窗尺寸、滚动区和弹层挂载方式。
- [ ] 已列出桌面分辨率和 Mac 滚动验收场景。
- [ ] 已确认不会向 `App.jsx`、`legacy.css` 继续堆叠实现。
- [ ] 已识别风险并准备回滚方式。

开发任务或 PR 描述必须附上这份检查结果。

## 5. 功能迭代标准流程

### 第一步：需求澄清

输出：功能范围、业务规则、角色权限、交互入口、异常情况、验收标准。

### 第二步：影响分析

输出：涉及文件、接口、共享组件、样式作用域、可能回归页面。

### 第三步：方案设计

输出：组件树、状态归属、Arco 组件选择、表格列定义、滚动模型、弹窗模型。

### 第四步：小步实现

- 数据/API、组件结构、样式、清理分别处理。
- 禁止同时大改业务逻辑和视觉。
- 每一步保持可构建、可运行。

### 第五步：开发自测

至少覆盖正常、空、加载、错误、超长文本、分页、筛选、权限和弹层。

### 第六步：代码清理

使用 `rg` 检查被替代函数、state、ref、className 和 CSS，确认没有第二套实现。

### 第七步：提交评审

提交业务保持清单、测试结果、视觉截图、风险和回滚方式。

## 6. 禁止合并清单

出现任一情况不得合并：

- 为修复一个页面新增全局 `table td` 规则。
- 通过复制表格或复制行实现冻结效果。
- 使用多个滚动容器叠加解决表头问题。
- Arco 已有组件但无说明地重新手写。
- 用大段内联 style 绕过 Token。
- 用 `nth-child()` 配置业务列宽。
- 表格 Tooltip 在横向滚动后留在原位置。
- Dropdown、Popover 被父容器裁切。
- 页面只有静态截图验证，没有实际点击、滚动和筛选验证。
- 新逻辑生效但旧逻辑、旧 CSS 仍保留。
- 修改了业务行为却没有产品确认。
- 构建产物被手工编辑。

## 7. 开发完成检查（Definition of Done）

- [ ] 原有业务行为和权限完整保留。
- [ ] 使用正确的 Arco 原生组件或已说明例外。
- [ ] 没有新增全局样式污染和重复 DOM。
- [ ] 表格、弹窗和弹层只有一个明确滚动模型。
- [ ] 超长文本、空数据和错误状态正常。
- [ ] 鼠标悬停、横向滚动、触底继续滚动无重叠和抖动。
- [ ] 1280、1440、1920 宽度验收通过。
- [ ] 键盘访问和 aria-label 检查通过。
- [ ] `npm run build` 通过。
- [ ] `git diff --check` 通过。
- [ ] 被替代代码和 CSS 已删除。
- [ ] PR 包含测试记录、风险与回滚说明。

```markdown
#### 状态与交互
- 正常：
- 加载：

```
