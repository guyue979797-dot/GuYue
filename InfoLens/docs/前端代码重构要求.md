# InfoLens 前端代码重构要求

> 文档版本：1.1（可执行任务书）\
> 制定日期：2026-08-02\
> 适用范围：`frontend/` 下全部代码及 `web/assets/` 前端构建产物\
> 设计基线：《鑫向晨 CRM 设计规范》v2.2\
> 组件基线：Arco Design React 2.66.x

> **开发前置要求**：任何前端功能开发、缺陷修复或重构开始前，必须先阅读 [`前端开发原则.md`](./前端开发原则.md) 并完成其中的“开发前置检查”。本文用于整体重构执行，日常功能迭代以《前端开发原则》作为第一入口。

## 0. 给开发人员的执行摘要

### 0.1 一句话目标

在不改变接口协议、权限逻辑和业务结果的前提下，把当前“单文件页面 + 大型遗留样式 + 多套表格实现”改造成“按业务域拆分 + Arco 原生组件 + 统一设计系统 + 可回归验证”的前端工程。

### 0.2 开发人员开始前必须确认

1. 阅读本文件和《鑫向晨 CRM 设计规范》v2.2。
2. 在重构前录制或截图保留现有核心业务流程，形成回归基线。
3. 不同时重写后端接口，不修改接口字段语义。
4. 不在一个 PR 中迁移多个业务 feature。
5. 每迁移一个页面，必须同时删除该页面被替代的旧 JSX 和旧 CSS。
6. 遇到本文与最新产品确认冲突时，以书面确认的最新需求为准，并在本文“例外记录”登记。

### 0.3 明确不做的事情

- 不更换 React、Arco 或现有后端技术栈。
- 不借重构修改业务统计口径、权限范围或数据结构。
- 不一次性推倒重写全部页面。
- 不直接编辑 `web/assets` 构建产物。
- 不为追求抽象而创建只有一个调用点、没有稳定职责的通用组件。
- 不以“构建通过”代替浏览器交互验收。

### 0.4 推荐实施方式

采用渐进式迁移：先建立基础组件，再按“终端明细 → 雪花政策 → 商品档案 → 图片处理 → 权限管理”的顺序逐页替换。每个页面迁移完成后即可独立上线和回滚，禁止大爆炸式重构。

## 1. 重构目标

本次重构不是视觉改版，而是建立可持续迭代的前端工程基础。完成后必须达到以下目标：

1. 页面、业务逻辑、数据请求、通用组件和样式职责分离。
2. 表格、筛选、分页、弹窗、状态反馈优先使用 Arco 原生组件。
3. 同类交互只有一个实现，禁止通过复制 DOM 或复制 CSS 完成功能。
4. 样式全部有明确作用域，不允许一个页面的规则污染其他页面或 Arco 内部组件。
5. 设计规范通过 Token 和基础组件落地，而不是在业务页面内重复硬编码。
6. 新功能可在独立 feature 目录内开发，不继续扩张单体 `App.jsx`。
7. 构建、交互回归、Mac 滚动边界和可访问性均有明确验收标准。

## 2. 当前问题与重构优先级

### 2.1 P0：必须先消除的结构风险

- `App.jsx` 超过 5000 行，页面、请求、表格、弹窗和工具函数混杂。
- `legacy.css` 超过 2500 行，存在历史规则、重复规则和高耦合选择器。
- 多张业务表仍使用原生 `<table>`，列宽、滚动、固定列和空状态各自实现。
- 曾使用复制左右冻结层的方式实现固定列，产生重复 DOM、悬停不同步、抖动和重叠。
- 存在 `table td`、`nth-child()`、`last-child` 等依赖 DOM 顺序或全局作用域的规则。
- Arco 表格和弹窗内部 DOM 被业务 CSS 直接覆盖，升级或结构变化时容易失效。

### 2.2 P1：持续迭代阻力

- 相同的加载、错误、空状态、分页和操作菜单在多个页面重复。
- 数据格式化、CSRF、下载、复制等基础逻辑集中在页面文件中。
- 大量内联 `style` 绕过设计 Token，无法全局统一。
- 页面筛选条件的布局、提交、重置和分页归零逻辑缺少统一约定。
- 缺少交互级自动回归，编译成功不能证明滚动、悬停和弹层正确。

## 4. 模块职责要求

### 4.1 App 层

- `App.jsx` 只负责会话、权限、应用布局和页面切换。
- 不允许在 App 层定义业务表格列、业务弹窗表单或 API 请求细节。
- 单文件建议不超过 300 行；超过 500 行必须拆分。

### 4.2 Feature 层

- 每个 feature 对外只暴露页面入口。
- 页面组件负责组合，不直接实现通用表格滚动算法。
- 数据请求和加载状态进入 feature hook 或 API 模块。
- 表格列定义与对应表格组件放在同一 feature 内。
- 弹窗必须独立成组件，禁止在页面 JSX 尾部堆叠多个大型 Modal。

### 4.3 UI 基础组件层

- 基础组件不得依赖具体 API 字段名。
- 通过明确 props 传入数据和回调。
- 统一封装 Arco 的稳定配置，例如 Dropdown 弹层容器、Table 空状态和 Modal 滚动区。
- 不允许基础组件反向引用 feature。

### 4.4 API 与工具层

- HTTP 错误统一转换为可展示的 `Error.message`。
- CSRF 获取和请求头拼装不得在每个页面重复。
- 日期、金额、数量、手机号等格式化函数放入 `utils/formatters.js`。
- 下载、复制等浏览器能力放入 `utils/browser.js`。

## 5. Arco Design 原生组件要求

### 5.1 强制优先使用

| 场景 | 必须优先使用 |
|---|---|
| 数据列表 | `Table` |
| 筛选选择 | `Select` / `Input` / `DatePicker` |
| 弹窗表单 | `Modal` + Arco 表单控件 |
| 截断文本 | `Typography.Text` 的 `ellipsis` |
| 状态 | `Tag` / `Alert` |
| 空状态 | `Empty` |
| 加载 | `Spin` |
| 行操作 | `Dropdown` + `Menu` |
| 分页 | `Pagination` |

原生 `<table>` 仅允许用于结构极简单、无滚动、无固定列、无排序、无分页的只读内容；使用前必须在代码评审中说明原因。

### 5.2 Table 强制规则

1. 所有列必须有稳定 `key` 或 `dataIndex`。
2. 除最多一个弹性列外，其余列必须明确配置 `width`。
3. 横向滚动使用 `scroll={{ x: "max-content" }}` 或列宽精确总和，禁止估算常量。
4. 禁止“虚拟滚动 + 左右双 fixed”组合。
5. 禁止复制 DOM 模拟冻结列。
6. 固定列必须由 Arco `fixed` 完成；若业务不强制冻结，优先不固定。
7. 表格只能有一个纵向滚动容器。
8. Mac 滚动容器必须设置 `overscroll-behavior: contain`，必要时使用统一边界钳制组件。
9. 表头固定必须固定 Arco 的完整 header 容器，不能只依赖独立 header table 内的 `th`。
10. 空状态、加载状态和分页必须由统一 DataTable/PageCard 结构承载。

### 5.3 单元格强制规则

- 常规单元格必须限制溢出，不得穿透相邻列。
- 截断文本统一使用 `Typography.Text ellipsis`，禁止手写 Tooltip 包裹截断文本。
- Tooltip、Popover、Dropdown 弹层必须挂载到 `document.body`。
- 操作列只保留“详情 + 更多菜单”。
- 操作列之外禁止使用 `overflow: visible`。
- 可点击数据必须使用 `<button type="button">`，保留键盘访问和 aria-label。
- 编码和金额使用统一格式组件，不在页面内重复格式化。

### 5.4 Modal 强制规则

- Modal 宽度使用预设：小 520、中 720、大 920；特殊情况需说明。
- 高度超过视口时，只允许 `.arco-modal-content` 内部滚动。
- Header 和 Footer 固定，滚动条不得出现在遮罩层或页面 body。
- 表单区使用 8pt 间距系统，禁止通过负 margin 修正布局。
- 命令式 `Modal.confirm` 只用于确认操作，不承载复杂表单。

## 6. 设计系统落地要求

### 6.1 Token 唯一来源

- 颜色、字号、间距、圆角、阴影必须引用 `tokens.css`。
- 业务 CSS 禁止新增设计规范已有的硬编码色值。
- 新 Token 必须先更新设计规范，再进入 `tokens.css`。
- Arco 主色通过主题变量覆盖，不逐组件重复设置主色。

### 6.2 样式作用域

- Feature 样式必须以页面根类开头，例如 `.customer-page`。
- 禁止裸写 `table`、`td`、`th`、`button`、`input` 等全局选择器。
- 禁止用 `nth-child()` 表达列语义；应使用 Arco column `className`。
- 禁止依赖“最后一列就是操作列”；必须显式使用 `.table-actions-cell`。
- 禁止使用 `!important`，仅允许修复第三方组件且必须附注释说明。
- 禁止在 JSX 中写大段内联样式；动态宽度/位移等运行时值除外。

### 6.3 legacy.css 退出策略

1. 冻结 `legacy.css`：不允许新增规则。
2. 每迁移一个 feature，将对应规则移至 `styles/features/`。
3. 对迁移后的页面执行选择器搜索并删除旧规则。
4. 当 `legacy.css` 清空后删除文件及 import。

## 7. 状态与请求规范

- 每个请求必须区分 idle/loading/success/error。
- 防止竞态：筛选和分页请求必须支持请求序号或取消机制。
- 筛选条件编辑态和已应用态分离；只有“查询”提交已应用条件。
- 筛选提交、重置和 pageSize 变化必须回到第一页。
- API 错误不得只写控制台，必须提供用户可见反馈。
- 禁止在 render 中发起请求或修改状态。
- URL 参数、筛选状态和接口参数的映射集中定义。

## 8. 可访问性要求

- 所有图标按钮必须有 `aria-label`。
- 可点击 Tag、数字和状态必须使用 button，而不是带 onClick 的 span/div。
- 表单必填项必须有可识别 label。
- Modal 打开后焦点进入弹窗，关闭后返回触发器。
- 键盘 Tab 可访问详情、更多菜单、分页和所有钻取入口。
- 禁止通过颜色作为唯一状态表达，必须同时提供文字或图标。

## 9. 性能要求

- 表格列定义使用稳定引用；复杂页面应使用 `useMemo`。
- 搜索联想和高频输入使用防抖，但查询按钮不延迟。
- 不重复请求同一静态选项；跨页面公共字典允许缓存。
- 图片列表必须懒加载，预览资源及时释放。
- 禁止为每一行注册 window 级事件。
- 单页不允许复制大数据数组仅用于展示排序；优先交给接口或 memo。

## 10. 删除与清理要求

以下代码发现后必须删除，而不是继续兼容：

- 未引用组件、函数、state、ref 和 CSS 类。
- 已由 Arco 组件替代的手写 Dropdown、Pagination、固定列和 Tooltip。
- 同一功能的第二套 DOM。
- 失效的媒体查询和历史截图修补规则。
- 仅为旧 DOM 顺序服务的 `nth-child()` 列宽。
- 构建产物中的手工修改；`web/assets` 只能由构建脚本生成。

删除前使用 `rg` 确认无引用；不得删除不属于本次 feature 的业务功能。

## 11. 测试与验收矩阵

### 11.1 每次提交必须通过

- `npm run build`
- `git diff --check`
- 浏览器无运行时错误
- 修改页面可正常加载、筛选、重置、翻页和打开详情

### 11.2 表格专项回归

每张数据表至少验证：

1. 1280、1440、1920 三种宽度。
2. 文本完整和超长两种数据。
3. 空数据、加载中、接口失败。
4. 横向滚动到两端。
5. 纵向滚动到顶部和底部后继续滚动。
6. 鼠标悬停行后再滚动。
7. 打开 Dropdown 后滚动。
8. 分页和 pageSize 切换。
9. macOS 触控板和普通鼠标滚轮。
10. Chrome 与 Safari；上线环境另补 Windows Chrome。

### 11.3 Modal 专项回归

- 768px 高度下 Header/Footer 可见。
- 内容滚动不带动页面。
- Select/Dropdown 不被裁切。
- 保存、取消、关闭和校验状态正常。

## 12. 重构实施顺序

### 阶段 A：基础设施

- 建立 UI 基础组件、API 层、格式化工具和组件样式。
- 冻结 `legacy.css` 和 `App.jsx` 的新增业务代码。
- 添加架构检查脚本和构建检查。

### 阶段 B：高风险页面

1. 终端明细：统一 Arco Table、滚动边界、标签折叠和筛选。
2. 雪花出库政策：迁移 Arco Table、政策进度和表单 Modal。
3. 商品档案：迁移 Arco Table、上传和详情。

### 阶段 C：图片与权限

- 拆分图片处理、归档、导出记录和终端明细 Modal。
- 用户管理迁移统一表格与操作菜单。

### 阶段 D：清理

- 删除 legacy.css。
- App.jsx 收敛到 300 行以内。
- 清除未使用代码和重复 API。
- 完成全页面回归后再合并上线。

## 13. 完成定义（Definition of Done）

全面重构完成必须同时满足：

- `App.jsx` 不超过 300 行。
- `legacy.css` 已删除。
- 所有主要数据列表均使用统一 Arco DataTable。
- 不存在复制 DOM 实现的冻结区域。
- 不存在无作用域的表格单元格规则。
- 所有截断文本使用统一组件。
- 业务页面、API、Hook、Modal 和 Table 已按 feature 拆分。
- 核心交互回归矩阵全部通过。
- 设计规范中的 Token、表格、筛选、弹窗和可访问性要求已落地。
- 重构前业务能力完整保留，无接口字段和业务规则丢失。

- 是否产生第二个滚动容器？
- 是否保留原有点击、筛选、导出和权限行为？

## 16. 标准组件接口约定

以下接口是目标形态，允许根据实际字段微调，但不得改变职责边界。

### 16.1 DataTable

```jsx
<DataTable
  rowKey="id"
  columns={columns}
  data={items}
  loading={loading}
  emptyText="暂无终端"
  scrollX="max-content"
  scrollY={tableHeight}
  pagination={{ page, pageSize, total, onChange, onPageSizeChange }}
/>
```

DataTable 内部统一负责：

- Arco `Table` 与 `Pagination` 组合。
- 单一纵向滚动容器。
- Mac overscroll 边界控制。
- 加载、空状态和错误占位。
- 表头固定、列宽校验和通用 className。

DataTable 不负责：请求数据、解释业务字段、打开业务弹窗。

### 16.2 TableText

```jsx
<TableText value={customer.customer_name} maxWidth={220} />
```

- 内部必须使用 `Typography.Text ellipsis`。
- 只有实际截断时显示 Arco 原生提示。
- 弹层挂载到 `document.body`。
- `null`、空字符串统一展示 `-`。

### 16.3 TableRowActions

```jsx
<TableRowActions
  onDetail={() => openDetail(row)}
  items={[
    { key: "edit", label: "编辑", onClick: () => openEdit(row) },
    { key: "delete", label: "删除", danger: true, onClick: () => remove(row) },
  ]}
/>
```

- 只渲染“详情”和“更多”。
- Dropdown 固定使用 `trigger="click"`、`position="br"`。
- `getPopupContainer={() => document.body}` 不允许业务页面重复配置。

### 16.4 FilterBar

```jsx
<FilterBar
  values={draftFilters}
  fields={filterFields}
  onChange={setDraftFilters}
  onSearch={applyFilters}
  onReset={resetFilters}
/>
```

- Select 类型筛选项排在 Input 前。
- 字段内部多选值采用 OR；不同筛选字段之间采用 AND。
- 查询、重置、回车提交和回到第一页行为统一。
- 页面只声明字段，不复制布局 CSS。

### 16.5 FormModal

```jsx
<FormModal
  size="medium"
  title="编辑标签"
  visible={visible}
  loading={saving}
  onCancel={close}
  onSubmit={save}
>
  {formContent}
</FormModal>
```

- Header/Footer 固定。
- Content 是唯一纵向滚动区域。
- Select/Dropdown 弹层不被裁切。
- size 只能使用预设值，禁止页面自由填写随机宽度。

## 17. 可领取的重构工作包

每个工作包独立分支、独立 PR、独立回归。人日为熟悉 React/Arco 的前端工程师参考值，不含产品重新确认需求的时间。

### WP-01 基础层与约束（2～3 人日）

**输入**：现有 tokens、通用组件、构建脚本。\
**输出**：`api/http.js`、`utils/`、UI 基础组件骨架、feature 样式目录、架构检查脚本。\
**验收**：旧页面行为不变；新基础组件具备最小演示或测试；禁止规则可在 CI 中发现。

### WP-02 终端明细（3～5 人日）

**输入**：`CustomerManagement`、`customers.css`、终端相关 Modal。\
**输出**：customers feature 完整拆分；统一 DataTable；删除终端旧表格和冻结层规则。\
**关键验收**：筛选、分页、详情、编辑、删除、批量新增；Mac 悬停与触底滚动；超长文本；多政策标签；页面无第二滚动层。

### WP-03 雪花出库政策（4～6 人日）

**输入**：`SnowPolicyManagement`、`snow-outbound.css`。\
**输出**：政策 feature；Arco Table；政策表单、详情、告警和终端钻取弹窗独立。\
**关键验收**：启停、排序、进度数字钻取、告警、核销、导入、新建/编辑、权限控制。

### WP-04 商品档案（2～4 人日）

**输入**：`ProductManagement`、`products.css`。\
**输出**：products feature；统一 Table、筛选、导入与表单。\
**关键验收**：月份、库存、导入、新增、编辑、详情、空数据和分页。

### WP-05 图片处理与归档（5～8 人日）

**输入**：App 中图片处理、批量任务、归档与导出逻辑，legacy.css 对应规则。\
**输出**：photos feature；提取、列表、归档、导出记录按职责拆分。\
**关键验收**：单条/批量任务恢复、选择照片、标签、归档、导出、错误提示及大图片性能。

### WP-06 用户与应用壳（2～3 人日）

**输入**：Users、Brand/Nav/App 布局。\
**输出**：users feature、AppLayout、navigation、权限入口。\
**关键验收**：超级管理员标签、增删改、菜单权限、Logo、面包屑、侧栏收起。

### WP-07 遗留清理与全量回归（3～5 人日）

**输入**：迁移后的全部 feature。\
**输出**：删除 legacy.css；App.jsx ≤ 300 行；删除无引用代码；完整回归报告。\
**关键验收**：本文第 13 节 DoD 全部达成。

**总体参考工作量**：21～34 前端人日。建议 1 名主程负责基础层和评审，1～2 名开发按 feature 并行；不要多人同时修改 App.jsx 和 legacy.css。

## 18. 每个工作包的施工步骤

开发人员对每个 feature 严格按以下顺序执行：

1. **建立基线**：记录接口、页面截图、关键操作和权限差异。
2. **列业务清单**：把按钮、筛选、弹窗、导入导出、钻取全部列出。
3. **先拆数据层**：移动 API 与 hook，保持 JSX 不变并验证。
4. **再拆视图层**：提取 Filters/Table/Modal，每次只移动一种职责。
5. **迁移 Arco**：原生 table 或手写控件替换为统一组件。
6. **迁移样式**：复制必要规则到 feature 作用域，使用 Token 改写。
7. **删除旧实现**：确认无引用后删除原 JSX、旧 state/ref 和旧 CSS。
8. **执行回归**：完成本文测试矩阵并保留截图或测试结果。
9. **控制提交**：数据层、视图层、样式迁移、旧代码删除分开提交。
10. **提交评审**：PR 描述附业务保持清单、风险点和回滚方式。

任何一步出现业务行为不一致，应回到上一稳定提交定位，不允许继续叠加 CSS 补丁掩盖问题。

## 19. 量化目标与预期收益

### 19.1 必须测量的工程指标

| 指标 | 当前基线 | 重构目标 |
|---|---:|---:|
| `App.jsx` 行数 | 约 5396 行 | ≤ 300 行 |
| `legacy.css` 行数 | 约 2537 行 | 0，文件删除 |
| 主要业务原生 table | 多处 | 主要数据表 100% 使用统一 Arco DataTable |
| 复制 DOM 冻结层 | 曾存在 | 0 |
| 无作用域 table/td/th 规则 | 存在历史风险 | 0 |
| 截断文本实现 | 多种 | 100% 统一 TableText |
| 主要页面重复分页实现 | 多处 | 统一组件覆盖率 ≥ 90% |
| 核心页面交互回归 | 主要靠人工反馈 | 关键流程 100% 有验收记录 |

### 19.2 合理的改善幅度预估

以下是完成全部工作包并经过 2～3 次后续迭代后的合理区间，不是承诺值：

| 维度 | 预期改善 | 说明 |
|---|---:|---|
| 代码可维护性 | 50%～70% | 单体文件拆分、职责明确、重复实现减少 |
| 新功能交付效率 | 25%～40% | 基础组件稳定后，表格/筛选/弹窗不再从零开发 |
| 表格与弹层类回归缺陷 | 降低 50%～75% | 单一滚动模型、统一 Arco 组件、专项回归 |
| 样式一致性 | 提高 40%～60% | Token 和作用域统一，减少局部截图式修补 |
| UI 视觉统一度 | 提高 25%～40% | 统一字号、间距、颜色、标签和操作层级 |
| 可访问性 | 提高 30%～50% | button、aria、焦点和键盘访问统一 |
| 首屏/交互性能 | 提高 5%～20% | 取决于拆包、图片懒加载和重复渲染清理，非本次最大收益 |

说明：代码重构本身不会自动让 UI “更漂亮”。UI 美感提升必须同时完成设计 Token、组件规范、间距层级和页面回归；如果只拆文件而不迁移样式，视觉提升接近 0。

### 19.3 如何验证收益

- 统计每个 feature 的文件行数、重复代码和 CSS 规则数量。
- 记录重构前后同类需求平均开发时长。
- 记录上线后一个月内表格、弹窗、筛选相关缺陷数。
- 对关键页面执行同尺寸截图对比，评审间距、对齐、层级和状态语义。
- 使用同一测试清单统计一次通过率，目标 ≥ 95%。

## 20. 风险、回滚与例外记录

### 20.1 主要风险

- 拆分过程中遗漏隐含业务行为或权限判断。
- 原生 table 迁移 Arco Table 后列宽、滚动或弹层行为变化。
- 删除 legacy CSS 时影响未迁移页面。
- 多人并行修改 App.jsx 导致冲突和重复实现。

### 20.2 控制措施

- 一次只迁移一个 feature。
- 每个 PR 保持可独立构建、运行和回滚。
- 删除旧 CSS 前用 `rg` 检查引用，并回归所有命中页面。
- 不把重构与业务需求混在同一提交。
- 高风险页面采用功能开关或保留上一稳定发布包作为回滚点。

### 20.3 当前已知产品例外

- 设计规范 v2.2 默认政策标签最多显示 2 个；终端明细页面曾确认可展示 4～5 个。实施时须由产品最终确认并登记为页面级配置，禁止通过修改通用组件默认值影响所有页面。
- 终端明细当前产品要求取消左右冻结列、页面和表头固定、仅数据区滚动；不得因设计规范的“标识列固定”建议重新加入冻结列。

### 20.4 例外登记格式
